# PR-023 primary-source research

Research date: 2026-10-16. Cloudflare limits and pricing below are from the official documentation versions shown; they are vendor limits, not an assertion that this project has a configured or production-tested Cloudflare account.

## Findings for the V2 decision

### Keep four version concepts distinct

The repository currently has several version layers that must not be silently collapsed: C-01's stored `schema_version`; the existing snapshot envelope `format_version`; the proposed V2 document version; and the render manifest version. D13 documents `FunnelSnapshotV1` and `RenderManifestV1`; the current domain compatibility check accepts schema version 1 and rejects missing or unsupported versions. Frozen C-01 also calls a missing schema version an error, and C-01_config currently lists only version 1 as supported. Therefore, “default V1 decoding” must not mean that an absent C-01 `schema_version` is accepted as V1. Preserve the existing V1 reader and define exactly which legacy envelope shape identifies V1; require an explicit version for new V2 documents/manifests. If V2 needs to change C-01 schema semantics, that is a separately governed contract question, not an edit to the frozen files. ([C-01](../../contracts/C-01_funnel.md), [C-01_config](../../contracts/C-01_config.md), [D13](../../decisions/D13_funnel_creation.md), [current compatibility code](../../../crates/domain/src/lib.rs), [PR-023 ledger](../../roadmap-pr-ledger.md#pr-023-v2-document-and-bounded-transfer-decision))

The official JSON Schema 2020-12 Core document defines `$schema` as the schema dialect and `$id` as a schema-resource identifier; neither is the application's document-version field. Use distinct, explicit instance fields for the V2 document and V2 manifest. A tagged `oneOf` with a `const` discriminator can select closed V1/V2 variants. `additionalProperties: false` only considers `properties` and `patternProperties` in the same schema object; when composing schemas, `unevaluatedProperties: false` is the keyword that accounts for properties evaluated by adjacent in-place applicators. Keep the validator dialect pinned and test its actual behavior. JSON Schema does not define EezFunnels' compatibility policy, stable-ID uniqueness across nodes, path-collision rules, or graph/edge validity; those remain domain validation responsibilities. The linked 2020-12 documents are the JSON Schema project's official specification pages, backed by informational Internet-Drafts published 2022-06-16 and expired 2022-12-18; they are not an Internet Standards Track RFC. ([Core §8.1, §8.2.1, §10.2.1.3, §10.3.2.3, §11.3](https://json-schema.org/draft/2020-12/json-schema-core.html); [Validation §6.1.3](https://json-schema.org/draft/2020-12/json-schema-validation.html); [Core draft metadata](https://json-schema.org/draft/2020-12/json-schema-core.html#section-boilerplate.1))

### Canonical bytes and portable digests

RFC 8785 (JCS; June 2020, Informational) produces deterministic JSON by requiring I-JSON input, removing insignificant whitespace, recursively sorting object keys by UTF-16 code units, applying ECMAScript primitive serialization, and emitting UTF-8. Arrays retain their order. It forbids duplicate property names, requires Unicode strings to be preserved as-is without Unicode normalization, and constrains numbers to IEEE-754 binary64; it recommends representing values needing more precision or longer integers as JSON strings. NaN and Infinity are errors. These constraints matter for cross-language hashes: identical-looking JSON text is not enough, and language-native key sorting or number formatting is not automatically JCS. ([RFC 8785 §§3.1, 3.2.1–3.2.4](https://www.rfc-editor.org/rfc/rfc8785); [security checks, §5](https://www.rfc-editor.org/rfc/rfc8785#section-5))

JCS defines canonical bytes, not a hash algorithm, digest field spelling, signature format, or EezFunnels manifest contract. D13 already uses SHA-256 for existing hashes, but that does not authorize reinterpreting V1 data. C-05 therefore names SHA-256 and the exact domain-separated UTF-8 inputs for the V2 document, theme-token map, and asset manifest; the V2 render manifest itself has no digest field. Recompute these values on the trusted side after parse and validation; do not trust a client-supplied digest as proof. Preserve V1 digest semantics. Test RFC vectors plus cross-runtime parity for non-ASCII property names, escaping, exponent/rounding cases, duplicate keys, and Unicode that differs only by normalization. This source establishes canonicalization rules, but not that a particular Rust or JavaScript library implements them correctly. ([RFC 8785 §§3.1–3.2.4, Appendix B](https://www.rfc-editor.org/rfc/rfc8785); [D13](../../decisions/D13_funnel_creation.md); [C-05](../../contracts/C-05_funnel_document_v2.md))

For the closed node model, use stable string IDs and tagged, finite node variants; validate uniqueness and references after decoding. JSON Schema can express object shape and discriminators, but ordinary schema validation is not a substitute for cross-node checks for duplicate IDs, route collisions, allowed edge targets, or acyclicity. Keep user-facing strings byte-for-byte stable through canonicalization unless a separately specified normalization step occurs before persistence.

### Interrupted R2 writes and finite cleanup

The current [Workers duration and runtime-update documentation](https://developers.cloudflare.com/workers/platform/limits/), checked 2026-10-16 (page updated 2026-10-12), says an HTTP Worker has no hard duration limit while the client remains connected. When the client disconnects or the response completes, associated tasks **may** be cancelled; `waitUntil()` extends work by up to 30 seconds. Runtime updates give in-flight requests up to 20 minutes to finish, while crashes, resource pressure, and shutdowns can interrupt work earlier. The documentation does not promise that an R2 `put()` is cancelled or settled within a fixed time after disconnect or Worker termination. D22 must not infer writer quiescence from the two-minute attempt lease, the two-minute cleanup grace, an HTTP response, or one early successful delete.

The [R2 Workers API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), checked 2026-10-16 (page updated 2026-07-31), documents that `put()` resolves with object metadata after a successful write, `list()` returns up to 1,000 lexicographically ordered objects per call, each object has an `uploaded` timestamp, and `delete()` is strongly consistent after its promise resolves and accepts up to 1,000 keys. It does not document cancellation of an unresolved `put()`. The [R2 object lifecycle documentation](https://developers.cloudflare.com/r2/buckets/object-lifecycles/), checked 2026-10-16 (page updated 2026-04-21), says objects are typically removed within 24 hours after their expiration time; this is not a precise cleanup deadline.

Therefore the proposal retires an abandoned D1 tombstone after a fixed 24-hour retention without reusing its globally unique R2 key. The stage is terminal and no future D1 transition may reference that key, so a later writer completion can only create an orphan. PR-024 must add a scheduled Worker sweep over the dedicated temporary-object prefix, enumerate with `list()` pagination, compare object `uploaded` time, exclude any live D1 reference, and issue repeatable deletes for unreferenced objects at least 24 hours old. Persist scan progress, finish a full pass, then restart from the beginning so keys inserted behind a cursor are eventually visited. If a late writer recreates an object after a sweep, its upload timestamp is new and a later pass catches it. Each invocation must cap work below the Cron 15-minute wall-time limit and continue on later invocations. This is a design path based on documented list/delete behavior, not a proved production deletion SLO; exact Cloudflare cancellation, Cron delivery, and R2 cleanup behavior remain integration gates before V2 staging is enabled. The ten-stage and ten-attempt quotas bound simultaneously retained D1 reservations only. Since an unresolved R2 operation may outlive its tombstone row, these quotas establish neither a strict provider-side in-flight operation cap nor an aggregate late-orphan byte bound. Make the D1 quota updates atomic with stage/attempt admission and cleanup; verify scheduler progress, cancellation behavior, and temporary-storage controls in PR-024 before enabling routes.

Cloudflare's docs describe each service's own limits; they cannot prove local Wrangler parity, remote-account configuration, cross-service atomicity, or that a stage token is correctly scoped. For the candidate protocol, the Worker/R2 route should write only temporary bytes. The small trusted owner command should mint a short-lived purpose-bound stage capability tied to funnel, base revision, document/manifest version, expected length and digest. The final save must independently verify stage scope/expiry, actual digest and length, schema, IDs/edges and limits, then commit the immutable D1 revision under the existing receipt/CAS behavior. Staging alone must neither save nor publish. Specify interrupted uploads, retries, single-use/overwrite rules, expiry cleanup, and concurrent save/cleanup races. The exact owner authority and capability lifecycle still require a local prototype.

There is also a useful aggregate-capacity check: C-01 allows 100 retained revisions per funnel, D14 allows 100 funnels, and D13 stores immutable snapshots. At the theoretical ceiling, 10,000 revisions × 1,048,576 bytes is 10,485,760,000 bytes (about 9.77 GiB / 10.49 decimal GB) of document bytes before manifests, indexes, receipts, or other rows. That exceeds decimal 10 GB by 485,760,000 bytes, while remaining below binary 10 GiB by 251,658,240 bytes; the cited D1 page says 10 GB and does not define a binary interpretation. Free's 500 MB per-database ceiling is lower still. This is a worst-case calculation, not observed usage. Keep the per-document 1 MiB limit as the ledger requires, but do not promise the full 100×100 maximum without an aggregate storage/retention budget and quota behavior. ([C-01_config](../../contracts/C-01_config.md), [D13](../../decisions/D13_funnel_creation.md), [D14](../../decisions/D14_workspace_funnel_limit.md), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/))

For a dated cost model, count D1 rows read/written and stored GB-month, R2 Class A/B operations and stored GB-month, and Worker inbound requests and CPU time. The current first-party pricing pages describe these billing meters: [D1 pricing, 2026-04-21](https://developers.cloudflare.com/d1/platform/pricing/), [R2 pricing, 2026-10-01](https://developers.cloudflare.com/r2/pricing/), and [Workers pricing, 2026-10-02](https://developers.cloudflare.com/workers/platform/pricing/). Record the date, plan, included allowances, and formulas with the prototype; the pricing pages cannot predict this project's operation counts.

### Snapshot versus typed patch: prototype, not assumption

Neither RFC 8785, JSON Schema, nor Cloudflare's limits decide whether snapshot or typed patch is better. Snapshot retains the current model's direct immutable read/restore/render path and consumes one full document per revision. A closed typed patch can reduce changed bytes for sparse edits, but adds patch validation/application, reconstruction, replay and restore costs, plus dependence on a valid base. Keep patches as finite typed operations over stable IDs; do not accept arbitrary JSON Patch paths. Any comparison that measures only request bytes misses the read, history, and recovery path.

The PR-023 Node harness covered the ledger's 1/10/25/50-page fixtures at 16 KiB, 128 KiB, 512 KiB, and 1,048,575 bytes, with sparse and 60%-broad text edits, 100 deterministically shuffled paired samples per fixture (exactly 50 samples of each candidate order), expected-output comparison, explicit upload/document boundary checks, and nine negative fixtures for unknown version, duplicate IDs, slug collision, invalid target, cyclic page graph, malformed JSON, excessive nesting, and a wrong patch digest. Across 32 fixtures and 6,400 measured candidate executions, every expanded patch matched its snapshot bytes/digest and no sample failed. Median upload-byte reduction was 98.38896% for sparse edits and 39.93208% for broad edits; combined typed-patch/snapshot p95 transform ratios were 1.7800, 1.7936, 1.8506, and 1.8622 at 16,384, 131,072, 524,288, and 1,048,575 bytes. The candidate meets the stated local gates of at least 25% median upload-byte savings in each family and no more than 2x p95 transform time at any size. This is a Node-only comparison, not two production-equivalent Worker/D1/R2 implementations; therefore D22 selects complete-snapshot transfer for the initial V2 runtime and does not accept the patch wire. A future decision may reconsider the exact tested `replace_text` grammar only after runtime-equivalent correctness, latency, memory, and provider-operation evidence; ineligible changes must use a complete-snapshot fallback if a patch is later approved. The result is not an end-to-end performance or provider-cost winner. The separate stage lifecycle model is checked headlessly for expired/consumed replay, stale-head rejection and fresh-key recovery, preservation/replay of prior mint receipts, retired-stage cleanup after replacement save/expiry, retry with an unresolved earlier upload, preservation of both attempt tombstones across remint, completion of each late writer, post-quiescence absence/delete checks, distinct stable keys for consecutive staged saves, same-key changed-payload rejection, save-receipt expiry, and replayable save receipts across revisions; it proves no Worker/D1/R2 behavior. Worker CPU, real D1/R2 operations, CAS races, browser serialization, current/oldest revision reads, 100-revision restore, concurrent workloads, and rendered-output parity remain unmeasured and must be verified by their implementing PRs.
