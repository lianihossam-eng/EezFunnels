# Future Cloudflare pilot readiness

This guide prepares an operator to rehearse a future EezFunnels pilot. It does not certify a production deployment, provision Cloudflare resources, run migrations, or publish a release. Repository CI and local Worker smokes are not evidence about a particular Cloudflare account.

## Before a pilot

Use a disposable Cloudflare account or isolated Worker with separate D1, R2, and KV resources. The operator provisions these resources and confirms their names and bindings in the intended Wrangler environment. Keep test submissions fictional and use a local reference receiver or an isolated receiver that cannot forward to a real destination.

Record the exact EezFunnels commit, `cargo xtask ci` result, hosted check results, Wrangler version, Worker name, D1 database name, R2 bucket, KV namespace, and migration list for the candidate. Follow [Deploy to Cloudflare](../deploy.md) for account setup; review [Security](../security.md) before exposing a host. Do not put tokens, signing keys, personal data, or recovery material in the issue, logs, or source control.

Before sending public traffic, verify that the dashboard, owner APIs, inbox, exports, reports, and recovery route are behind Cloudflare Access or an equivalent perimeter. Confirm the public hostname and `PUBLIC_BASE_URL`, custom-host mappings, D1/R2/KV bindings, scheduled triggers, and local-to-remote environment separation. Configure secrets using Wrangler's secret mechanism. Leave webhook delivery disabled until an operator has reviewed the HTTPS destination, field mapping, signing secret, retry behavior, and receiver deduplication. Leave `INTERACTION_REPLAY_KEY` unset to keep the interaction collector disabled. If enabling it, review the default 30-day retention and 100-events-per-minute limit per funnel, or set valid account-appropriate values; collection still requires the visitor's separate measurement consent.

## Rehearsal checklist

Use the repository's local CI and browser smokes for behavior that relies on the in-process reference receiver. On an isolated Worker, verify the remote behaviors below using fictional data and only destinations hosted by the operator:

1. Create a contact, estimate-request, or diagnostic-request funnel; edit, save, publish, preview, and unpublish it. Confirm that the success page acknowledges receipt only and makes no booking, price, diagnosis, or response-time promise.
2. Submit valid and invalid forms. Correct a field error without losing allowed values, and confirm that an uncertain retry reuses the original idempotency key rather than creating another submission.
3. Check the inbox, follow-up history, private export, targeted erasure, retention boundary, and report coverage. Verify that request acknowledgement, marketing consent, and measurement consent stay independent.
4. Rehearse webhook delivery to a reachable, operator-controlled HTTPS test receiver that cannot forward to a real destination. Verify signature validation, stable event identity, selected fields, retries, terminal failures, cancellation, and duplicate handling. The local reference receiver is in-process and cannot receive requests from a remote Worker. An HTTP acknowledgement means only that the receiver accepted the request.
5. Export a saved V2 template and import it into a new unpublished funnel. Check missing media and explicit replacements from the target library; confirm that no private brief, submission, delivery configuration, or secret appears in the template.
6. Rehearse Worker rollback and D1 recovery separately on disposable resources using the rollback section below. Record the result and recovery time without copying secrets or submission values.

## Rollback and recovery

Worker code rollback and D1 recovery affect different state. A Worker version rollback changes the code/configuration serving traffic; it does not restore D1, R2, or KV, and Cloudflare activates the selected version immediately across its routes and domains. Before invoking rollback, restrict public HTTP ingress with an independently controlled perimeter while keeping any required recovery access available. Verify the candidate version against the live D1 schema, bindings, erasure/recovery gate, and delivery source-suppression behavior first. A schema-compatible Worker from before targeted erasure can still expose a suppressed D1 row while its R2 journal is pending. If the candidate cannot preserve the current erasure and delivery invariants, keep traffic held and use a compatible version or fix. After rollback, check `/health`, the dashboard perimeter, one public page, a form, and the private inbox before removing the ingress hold. Cloudflare's version behavior and account-specific controls are summarized in the [rollback research note](../research/public-pilot-cloudflare-rollback.md).

For suspected D1 data loss or schema damage, preserve the current database state and independently hold public HTTP ingress and scheduled dispatch before starting recovery. Cloudflare Access protects HTTP routes; it does not stop Cron invocations. Do not treat Worker rollback as a database restore, and do not restore D1 before closing the EezFunnels recovery gate. Follow the [submission erasure and D1 recovery runbook](submission-erasure.md): close submissions, prepare until erasure intents are journaled in the original R2 bucket, restore D1 while retaining those R2 journals, and apply the required migrations. A D1 restore can also rewind a delivery task to `pending` after its receiver already accepted the request; compare restored tasks with the receiver's ledger of stable event IDs and require deduplication before dispatch resumes. Before the final reconciliation, verify that the active Worker, schema, destination configuration, and delivery decisions are compatible. Reconciliation reaching `ready` automatically opens the EezFunnels gate; scheduled dispatch can resume immediately, and the application has no separate dispatch-pause control. Establish any required independent dispatch hold before that point. Remove ingress and dispatch holds only after recovery and compatibility checks are complete.

Cloudflare Time Travel retention, eligible database backend, and restore limits depend on the actual account and must be checked before any real restore. A D1 restore is destructive to the selected point-in-time state; retain the returned bookmark for the documented undo path. Cloudflare does not restore EezFunnels' R2 journals as part of a D1 restore. The recovery guarantee is bounded by the original R2 journal remaining intact and the configured erasure horizon. See the source-backed [Cloudflare pilot and rollback research](../research/public-pilot-cloudflare-rollback.md) for the platform boundary and official references.

The series tested the application gate with local D1 rows and local R2 journals. It did not run a Cloudflare deployment, remote migration, Time Travel restore, R2 recovery, or delivery to a remote receiver. Rehearse those account-specific operations before a pilot, and do not describe repository CI as production verification.
