# Deliver submissions through an operator-configured signed webhook

Status: accepted for the public improvement series.

Support one HTTPS destination configured by the installation operator, disabled by default, with per-form field selection and versioned destination/mapping definitions. Commit a delivery task atomically with an accepted submission, store immutable source references rather than a second persistent copy of submitted values, and reconstruct a deterministic body from the retained source. Sign each request with HMAC-SHA-256 using a separate Worker secret; reject redirects and bound requests to a 10-second timeout, five attempts within 24 hours, and the source's retention expiry. Do not backfill old submissions or retarget an existing task when configuration changes. A 2xx response means only that the receiver accepted the request; duplicates remain possible and the receiver owns deduplication.

## PUB-008 acceptance storage

The installation has one current destination-version pointer, seeded disabled, and each enabled form mapping names both its immutable mapping version and the destination version its owner approved. If the installation destination changes, a form remains inbox-only until its setting is explicitly updated to a mapping for that destination. A missing setting, a disabled installation/form, or a destination-version mismatch never blocks inbox acceptance.

`Repository::store_public_form_submission` owns acceptance and optional outbox creation in one ordered D1 batch. It reads the canonical source ID for the idempotency tuple, conditionally inserts the source using the existing publication, retention, rate, and erased-key checks, then immediately inserts a reference-only task only when the source insert changed one row. A handled duplicate or a replay with a new candidate UUID cannot enqueue an existing source. The task ID is the canonical submission UUID; the task freezes its submission, page, form, revision, destination-version, and mapping-version references. Submitted values, consent copies, fingerprints, keys, secrets, and serialized payloads remain in neither the task nor its schema.

The no-insert path performs the existing classification query after the D1 batch so time-bound replay-marker checks and error precedence remain as before. A failed task insert rolls back the accepted source with the D1 batch; the public request returns the existing uncertain-storage response and can be retried with the same idempotency key. There is no insert trigger, public enqueue method, CLI/MCP command, or historical backfill: direct source insertion for fixtures or restoration does not synthesize tasks.

While a task exists, D1 rejects changes to source identity, accepted values, consent evidence, channel, and timestamps needed to reconstruct its request. The owner may still update the inbox triage status. Destination and mapping versions and task references cannot be edited in place. Source deletion cascades to its task. Starting targeted erasure writes the intent and replay marker and deletes the task in the same D1 batch; the retained-visible task view also excludes expired or intent-hidden sources. PUB-009 must use that view, require the independent R2 recovery-ready gate, and recheck source visibility immediately before transport. Before producing a body, it must validate the frozen selected field IDs against the form in the task's exact source revision and fail closed if that mapping is incompatible. PUB-010 may warn the owner when later edits make the current mapping incompatible, but that warning does not replace PUB-009's dispatch-time check. These D1 rules do not establish R2 readiness and cannot recall a request already sent.

The local Worker/D1 smoke verifies `changes()` after `INSERT ... RETURNING`, duplicate and concurrent retry behavior, default inbox-only acceptance, no backfill, explicit destination revalidation, rollback on an injected outbox error, task/source immutability, and erasure/recovery visibility. Cloudflare's batch contract and the runtime experiment are recorded in [the PUB-008 D1 research note](../research/public-outbox-d1.md). No remote delivery is performed by this PR.
