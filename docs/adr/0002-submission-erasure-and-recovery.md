# Erase submissions with a bounded recovery journal

Status: accepted for the public improvement series.

A targeted owner deletion first hides the submission and suppresses pending delivery, writes a minimal private journal to R2, then purges the D1 row; each step must be retryable. The journal retains enough technical references to match a restored D1 row without storing its submitted values. Anti-replay markers use a domain-separated SHA-256 digest of an unambiguous canonical encoding of the funnel, form, and submission-key context, never a field-value fingerprint. A marker blocks that key only through the latest original expiry among erased submissions that reused the same context; an older journal must preserve a newer marker instead of shortening it. Keep each R2 journal for the greater of source expiry or deletion time plus the declared recovery horizon, which defaults to 30 days and is configurable from 1 to 3,650 days. The restore guarantee applies only when D1 is restored with the R2 journal intact and the journal is reapplied before reads and dispatch resume; this avoids a permanent identifier-based suppression list while making the recovery limit explicit.

## Runtime contract

Migration `0017_public_submission_erasure.sql` stores independent D1 erasure intents and digest-only replay markers. An intent has no foreign key to the submission, funnel, or revision, so it survives expiry cleanup and cascade deletion while an R2 journal write is pending. Inbox, status, export, and completion-report reads exclude a source with a pending intent. Public submission insertion checks the same identity digest in the insert statement; a matching erased key receives the existing generic idempotency conflict until the marker's latest original expiry, regardless of changed form values.

The owner can export one retained response at `GET /api/submissions/:submission_id/export` or target it with `DELETE /api/submissions/:submission_id`. A delete returns `204` only after an exact versioned journal is durable at `private/submission-erasure/v1/<submission-id>.json` and D1 has purged the source and intent. A failed R2 write leaves the source hidden and the intent pending for bounded scheduled retries. Journal cleanup reads and validates each journal's own frozen retention deadline.

The R2 control object at `private/submission-erasure-control/v1/recovery` is the authoritative submission-operation gate. It is initialized conditionally only when no intent, marker, or journal exists; a missing control with erasure history fails closed. Recovery uses the phases `ready`, `preparing`, `awaiting_restore`, `draining_restored_intents`, and `reconciling`. An operator closes the gate, drains already-admitted requests before the final pending-intent check, restores D1 while retaining R2, then explicitly starts reconciliation with the same generation. Each bounded journal page is applied idempotently before its R2 cursor advances. A restored source is deleted only after its funnel/form/key digest and original expiry match the journal. The gate returns to `ready` only after a complete terminal page and a final no-pending-intent check. There is no general-purpose reopen action.

The implementation and operator sequence are documented in the [submission erasure runbook](../runbooks/submission-erasure.md). The application cannot cancel an already-admitted Worker invocation or detect an out-of-band D1 restore; the operator must drain those invocations before restoring the database. PUB-007 adds no delivery outbox. Later delivery work must use the same gate and visible-source predicate, suppress unstarted tasks on erasure, and document that a request already sent to a receiver cannot be recalled.
