# Preserve canonical documents with explicit renderer capabilities

Status: accepted for the public improvement series.

Keep the document and schema at V2 for additive content, and omit absent optional fields during serialization so existing canonical bytes remain unchanged. Use an explicit renderer capability table to preserve renderer v3 through v7 behavior; add renderer-v8 for locale and form presentation, renderer-v9 for section, telephone, and email button destinations, renderer-v10 for FAQ and ordered-step blocks, renderer-v11 for structured offer pricing and comparisons, and renderer-v12 for contextualized evidence. Reject a publish or save that requires an unsupported capability instead of silently dropping content. This keeps existing revisions readable while allowing the product to add typed content without pretending old renderers understand it.

V2 button actions remain one tagged sum: page navigation, same-page section navigation, HTTPS, telephone, or email. Section targets use `SectionId` and must resolve on their source page; deleting a target section removes incoming section actions in the same edit so undo restores both together. Telephone values are reduced to an optional leading plus and 3–15 digits, while email values use the existing mailbox validation and are percent-encoded when written into a `mailto:` URI. Renderer-v9 adds stable section anchors and these three action capabilities; v3–v8 retain their exact action and section markup behavior.

We chose additive variants on `ActionV2` over a generic URI action, which would admit schemes the renderer must not support, and over a nested contact-action union, which would add another wire shape without reducing caller knowledge. We accept that older renderer manifests cannot serve these destinations; such revisions fail closed instead of becoming partially interactive.

The v3–v9 capability contract is exact: v3 renders the entry page only; v4 adds multipage routes; v5 adds native forms; v6 adds digest-bound images; v7 adds SEO metadata; v8 adds an optional public language, form presentation, and multiline presentation for existing text fields; v9 adds section, telephone, and email button destinations. Renderer-v10 adds FAQ and ordered-step content, limited to 1–12 items, 2,048 bytes per field, and 16 KiB of combined text per block. Their nested item records raise the bounded document parser depth from eight to nine without changing the document or schema version. Renderer-v11 adds structured offer cards and comparisons. Offer amounts are bounded exact decimal strings, so no binary floating-point calculation changes the authored value. An announced total is entered separately and is never derived from recurring amounts. A comparison references its offer sources so its scope, prices, and conditions stay aligned with their cards. Offer blocks render with semantic HTML and a horizontally scrollable comparison table. Renderer-v12 adds evidence blocks for testimonials and case studies, with a demonstration/real status sum type, required attribution/date-or-period/scope on real items, visible limitations, and optional digest-bound references to existing image assets. Demonstration content receives a fixed visible label; incomplete evidence blocks are rejected by publication readiness. Renderer-v3 through v11 retain their explicit feature profiles and reject evidence content instead of dropping its status or context. The published route keeps the historical v3/v4 form rejection at render time. Renderer profiles are consulted for both capability validation and output routing so a new renderer version cannot shift older feature sets.

Evidence uses one shared block shape because testimonials and case studies share the same presentation contract. The status is a discriminated type: demonstration content carries no client attribution, while real content cannot be represented without attribution, date or period, and scope. This keeps demonstrations from accidentally inheriting client context and gives the editor and renderer one content module to maintain.

Public language is optional in the V2 document and resolves to English when absent. Missing additive fields remain omitted from canonical serialization. Changing a document's public language changes renderer-owned text and defaults for newly created content; it does not translate content or consent text authored earlier. Multiline text normalizes CRLF and CR to LF before validation, recovery, persistence, and retry fingerprinting while keeping the existing text submission type and scalar-count limits.
