# PUB-009: Cloudflare signed-webhook delivery research

Checked against primary sources on 2026-10-30. This note records platform behavior and implementation guidance for the accepted [webhook-delivery contract](../adr/0003-webhook-delivery.md); it is not evidence from a deployed Worker or live receiver.

## Documented platform behavior

- **Cron events and local tests.** Cron Triggers run on UTC. Each configured expression invokes the same scheduled handler; the event exposes the exact configured expression, so separate dispatch and cleanup jobs can branch on it. The Rust `worker` binding used by this repository (`0.8.3`, see [Cargo.lock](../../Cargo.lock)) exposes that value as `ScheduledEvent::cron()`, as shown in the [workers-rs source](https://github.com/cloudflare/workers-rs/blob/v0.8.3/worker/src/schedule.rs). Cloudflare awaits the promise returned by `scheduled()` for up to the Cron wall-time limit; `waitUntil()` is for registering additional work or recording its outcome, not required for the main awaited dispatch. Wrangler can invoke the handler locally through `/cdn-cgi/local/scheduled` with `cron` and `time` query parameters. Local Explorer requires Wrangler 4.139.0 or later; this repository pins 4.153.0 in [package.json](../../package.json). [Scheduled Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/), [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

- **Outbound Fetch behavior.** A newly constructed Worker `Request` defaults to `redirect: "follow"`, and following redirects forwards request headers to the redirect destination. `redirect: "manual"` returns a 3xx response without following it; Workers do not implement `redirect: "error"`. A request can be cancelled with an `AbortSignal`; Cloudflare documents that `AbortSignal.timeout()` needs an active request context because it schedules a timer. [Request](https://developers.cloudflare.com/workers/runtime-apis/request/), [AbortSignal changelog](https://developers.cloudflare.com/changelog/post/2026-08-19-abort-signal-global-scope/)

- **Outbound routing and private destinations.** Worker `fetch()` subrequests use Cloudflare DNS resolution and accept URLs rather than raw IP addresses. The `global_fetch_strictly_public` compatibility flag affects requests to the Worker's own zone. Cloudflare separately documents private-network access through explicit Workers VPC bindings. These documents do not establish a general SSRF filter or guarantee that every hostname resolves only to a public address. [Known issues](https://developers.cloudflare.com/workers/platform/known-issues/), [compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/), [Workers VPC](https://developers.cloudflare.com/workers-vpc/configuration/vpc-networks/)

- **Secrets and HMAC.** Worker secrets are encrypted text bindings exposed to Worker code through `env`; Cloudflare recommends secrets instead of plaintext `vars` for sensitive values. Local development may load them from `.dev.vars` or `.env`, which must not be committed. Workers' Web Crypto implementation supports HMAC `sign()` with SHA-256; [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html) defines HMAC as message authentication, not encryption. [Secrets](https://developers.cloudflare.com/workers/configuration/secrets/), [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [Cloudflare signing example](https://developers.cloudflare.com/workers/examples/signing-requests/)

- **D1 transaction and concurrency behavior.** `D1Database.batch()` runs its statements in order, non-concurrently, as one SQL transaction; if a statement fails, D1 aborts or rolls back the sequence. A D1 database is single-threaded and processes queries one at a time; excess concurrent requests queue and may return an overload error. A batch transaction covers D1 statements only and cannot include an outbound HTTP request. [D1 Database](https://developers.cloudflare.com/d1/worker-api/d1-database/), [D1 FAQ](https://developers.cloudflare.com/d1/reference/faq/)

- **Runtime limits.** Cron has a 15-minute maximum wall time, but a sub-hour Cron has plan-specific CPU limits (10 ms on Free and 30 seconds on Paid in the current limits table). Time waiting on network I/O is wall time, not CPU time. For a scheduled handler, the returned promise is awaited; the separate 30-second `waitUntil()` extension documented for HTTP requests is not the Cron budget. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Scheduled Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/)

## PUB-009 implementation recommendations

1. Keep cleanup on its current `*/15 * * * *` trigger and add the planned `* * * * *` dispatcher. Branch on the exact `ScheduledEvent::cron()` string because Cloudflare passes the configured expression character-for-character. Exercise both paths locally with Wrangler's scheduled-event test support; this invokes the local handler and does not require a deployment or receiver. [Current schedule](../../wrangler.toml), [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

2. Use D1 as the durable retry and lease authority. Select candidates from the retained-visible task/source view, require the R2 recovery gate to be ready, then claim work with one conditional D1 state transition and verify exactly one row changed. Commit the lease before making the HTTP request; do not hold a D1 batch open across network I/O. Recheck recovery readiness, source visibility, expiry, and the frozen mapping against the task's exact revision immediately before transport, as required by the [delivery ADR](../adr/0003-webhook-delivery.md) and [erasure runbook](../runbooks/submission-erasure.md). A concurrent scheduled invocation must be safe to run because a prior invocation may still be in progress: Cloudflare allows up to 15 minutes of scheduled wall time while this dispatcher runs every minute. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

3. Build the deterministic body from the immutable source reference, define and test one versioned bytes-to-sign format, and sign with Web Crypto HMAC-SHA-256 using a separate Worker secret. Fail closed before transport when the secret is absent. Keep local tests on a fake secret in ignored `.dev.vars`; never provision a production secret as part of this PR. HMAC authenticates bytes but does not hide them, so HTTPS remains necessary. The [PUB-008 D1 note](public-outbox-d1.md) and delivery ADR define source immutability, destination/mapping versioning, and duplicate-delivery constraints.

4. Parse and validate the installed operator destination as HTTPS; never accept a destination from visitor input. Use `redirect: "manual"` and classify any 3xx as a failed attempt. Apply the plan's 10-second timeout with a request-scoped abort signal. Since the Cloudflare documentation cited above does not promise a universal private-hostname block, do not describe Workers `fetch()` as the SSRF safeguard; retain operator-only configuration and validate/reject invalid destinations in the application. This is a defense policy, not a Cloudflare routing guarantee.

5. Bound the amount of work per invocation so the one-minute schedule can recover after failures and not consume the wall-time or plan-specific CPU budget. A timeout, connection loss, or crash after the receiver accepted the request can leave the result uncertain. Persist bounded retries for no more than five attempts/24 hours and stop at source expiry, using the same stable logical delivery ID each time. Do not claim exactly-once delivery; the receiver must deduplicate. The application-level retry limits and duplicate semantics come from the accepted [delivery ADR](../adr/0003-webhook-delivery.md), not from Cron or D1 guarantees.

Local acceptance should cover both cron expressions, conditional concurrent claims, timeout, 3xx, 429/5xx, terminal response, ambiguous response after receiver acceptance, crash/retry, configuration change, and source erasure/expiry. A test-only receiver or request stub should verify signature bytes and deduplication without contacting a real destination.

## Boundary of the evidence

Cloudflare documents the handler, Fetch, secrets, D1, and local test mechanics cited above. The lease design, destination policy, retry count, request timeout, source rechecks, receiver deduplication, and failure matrix are PUB-009 implementation requirements or recommendations. This research did not deploy a Worker, provision a remote secret, contact any webhook receiver, or establish production behavior.
