# Cloudflare pilot and rollback research

Research snapshot: 2026-10-31 UTC. The official [`cloudflare/cloudflare-docs` production tree](https://github.com/cloudflare/cloudflare-docs/tree/9bf9be5d174c8824ea1e259bd84b03867f7b29fc) was read at commit `9bf9be5d174c8824ea1e259bd84b03867f7b29fc` (commit time 2026-10-31 12:34 UTC). Recheck the linked Cloudflare guidance, account plan, and Wrangler version before a future remote pilot; this note is preparation, not a deployment instruction or production-readiness claim.

## Findings for the operator guide

- A Workers version contains the Worker code/configuration, bindings, and compatibility settings; it does not snapshot the state of bound D1, R2, KV, or Durable Objects. A deployment chooses which Worker version receives traffic. Default `wrangler deploy` uploads and activates a version at 100%; the version upload and traffic change can instead be separate operations. See Cloudflare [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/) and [Deployment management](https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/).
- A Worker rollback creates a new active deployment using a previous Worker version and does not roll back connected resources. Cloudflare documents rollback of up to the 100 most recently published versions and warns that an older version may fail against changed storage structures or bindings. A code rollback therefore does not restore D1 data or undo migrations. See [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) and the [`wrangler rollback` command](https://developers.cloudflare.com/workers/wrangler/commands/workers/#rollback).
- D1 Time Travel is point-in-time recovery for databases on the production storage backend. Cloudflare's current documentation states 30 days of history for Workers Paid and 7 days for Workers Free, with a limit of 10 restore operations per database per 10 minutes. Verify the actual database backend with `wrangler d1 info <DATABASE_NAME>` (`version: production` supports Time Travel); account limits and retained history must cover the intended recovery window. See [Time Travel and backups](https://developers.cloudflare.com/d1/reference/time-travel/) and [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- A D1 Time Travel restore overwrites the database in place and cancels in-flight queries/transactions. It returns a previous bookmark that can be used to undo the restore. This operation is destructive and separate from Worker version rollback. See [restore and undo](https://developers.cloudflare.com/d1/reference/time-travel/#restore-a-database).
- D1 migrations are ordered SQL files; Wrangler records applied migrations in `d1_migrations`. Use the immutable database name when inspecting or applying migrations to reduce the chance of targeting a different binding. See [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/).
- Cloudflare's snapshot-backup page is explicitly marked **Legacy**. It states a planned removal date of 2025-07-01 for alpha snapshot backups, which predates this research snapshot; confirm current service availability rather than relying on that interface. Production-backend D1 uses Time Travel instead. Do not prescribe `wrangler d1 backup` as the recovery path for a current production-backend database. See [Backups (Legacy)](https://developers.cloudflare.com/d1/reference/backups/).

## EezFunnels recovery boundary

Cloudflare restores D1 only; its Worker-version history does not include the R2 objects on which EezFunnels erasure recovery depends. Before a D1 restore, keep the existing R2 bucket and its erasure journals intact, close submission operations, drain erasure intents, and complete reconciliation before allowing reads or delivery to resume. The exact guarantee is limited to a restored D1 database with the original R2 journals intact and reconciliation completed within the documented horizon. Follow the repository's [submission erasure and D1 recovery runbook](../runbooks/submission-erasure.md); its recovery gate is an EezFunnels invariant, not a Cloudflare feature.

A future pilot guide should distinguish these two paths:

1. **Worker-only regression:** independently restrict public ingress while keeping any required recovery access available. Verify that the previous Worker version is compatible with the live D1 schema, bindings, erasure/recovery gate, and delivery source-suppression behavior before invoking rollback; Cloudflare activates that version immediately and leaves bound storage unchanged. A schema-compatible build from before targeted erasure can still reveal a suppressed D1 row while its R2 journal is pending. Verify health and core routes before removing the ingress hold; if the candidate cannot preserve current erasure invariants, keep the hold in place.
2. **D1 data/schema recovery:** independently hold public ingress and scheduled dispatch, then follow the application's prepare → restore → migrate → reconcile sequence. Verify the active Worker, restored schema, destination configuration, and delivery decisions before final reconciliation. A D1 restore can rewind delivery attempt state after a receiver has accepted a request; reconcile restored tasks with the receiver's stable event-ID ledger and deduplication behavior before dispatch resumes. When the recovery endpoint reaches `ready`, EezFunnels automatically opens the gate and scheduled dispatch can resume; there is no separate application dispatch-pause action. Keep any required external hold in place until recovery verification is complete. Never treat a Worker rollback as a substitute for D1 recovery.

Before any real pilot, rehearse both paths on disposable resources with the same Wrangler configuration and migration set. Validate the restore bookmark/retention available to the account, recovery-gate behavior, R2 journal availability, migration state, health route, public form submission, and owner inbox after recovery. Keep secrets and the operator perimeter configured independently of public form content. No remote deployment, migration, backup, restore, or receiver delivery was performed for this research.
